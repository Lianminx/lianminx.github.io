和 Cursor 协作时固定下来的几条规则

Dec 12, 2024 · 1 分钟阅读

这些规则是为了让一次对话的上下文可预期，不是为了把操作步骤写全。

新项目从空目录开始。上一个项目的文件留在工作区里，模型会把它们当成这次的需求。需求说具体，但不要在还没看过代码时把实现细节说死。项目一开始就写 README，后面的对话有地方引用目标，而不是每次重新描述。

用 git 保留可以退回的版本。生成结果不可靠时，退回比在错误版本上继续改便宜。用 Composer 开始一个改动，并把代码库放进上下文，避免它只看见当前打开的文件。常用文档放进 Docs，同一份接口说明不必每次重贴。反复出现的约束写进 Rules，例如语言、目录和不能改的模块。

有一条后来停了：要求它给每一块代码写注释。注释和代码会分开过期，过期的注释比没有注释更误导。空目录、README、git 和 Rules 还在用。
