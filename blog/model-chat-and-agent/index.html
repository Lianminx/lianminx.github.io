模型对话接口与 Agent 本质

Nov 21, 2026 · 3 分钟阅读

模型对话接口是用结构化上下文和模型交互。Agent 是围绕一个目标，反复组织这份上下文、调用模型，再根据输出决定下一步，直到任务完成。接口状态只说明这一次调用。任务有没有结束，由 Agent runtime 判断。

我一开始把 /chat 和 /Responses 看成返回内容的差别：chat 只给回答，Responses 再附上思考过程。这个差别不是重点。两边都能多轮对话，也都能调用工具。要分开的是三件事：一条记录里有哪些角色，上下文放在调用方还是服务端，一条记录能装下什么。

一条记录里有哪些角色

传统 Chat 以 Message 为基本单位，用 Role 区分消息从哪来。

Role 放什么
System / Developer 行为规范、提示词、约束。工具和 Skill 的描述也在这里
User 用户输入和任务要求
Assistant 模型的回答，以及它发出的工具调用请求
Tool 工具执行完的结果，供下一轮推理使用

工具调用和工具返回不要放在同一个角色里。调用请求是模型给出的，记在 Assistant。执行结果是工具给出的，单独记为 Tool，再作为后续输入送回模型。

上下文放在哪

Chat 的输入输出就是上面这种 Message。每一轮请求都带上前面几轮，上下文由调用方在本地管理。

Responses 可以把同一次会话用请求 ID 串起来。之后每次只提交必要字段，服务端按这个 ID 找回前面几轮。它也支持和 Chat 一样，不在服务端保存，由本地自己带上上下文。我现在用的是 Responses，并且关掉了服务端存储。

一条记录能装下什么

Chat Completions 以消息列表为核心。Responses 用 Item。同一套结构里可以放文本、工具调用、工具结果、推理数据和多模态内容。Responses 更统一，一条记录能表达的内容也更多。多返回一段思考过程，不是这两套接口的分界。

任务什么时候算结束

Agent 不靠一次调用做完。它先有目标，然后持续组织上下文，多轮调用模型。每一轮看模型输出，决定下一步是调用工具，还是停。

Chat 用 finish_reason 说明这一次生成：

  • tool_calls：模型还要调用工具
  • stop：这次生成停了

Responses 用 status 说明这一次 Response：

status 含义
completed 本次生成完成
in_progress 正在生成
incomplete 响应没有完整完成
failed 执行失败
cancelled 已取消
queued 等待处理

这些状态回答的是这次调用怎样了。正常的任务结束，是 runtime 看到没有后续工具调用。异常结束有多种情况，要分开判断，不能拿一次 finish_reason 或 status 当成任务结果。
