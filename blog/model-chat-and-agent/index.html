模型对话接口与 Agent 本质

Nov 21, 2026 · 2 分钟阅读

我一开始以为，模型厂商的 /chat 只返回回答，/Responses 会附带思考过程。要说清楚的不是这个差别。

模型对话接口本质上是通过结构化上下文与模型交互。传统 Chat 接口以 Message 为基本单位，用 Role 区分消息来源：

  1. System / Developer：定义模型的行为规范、提示词和约束。工具和 Skill 的描述也在这里。
  2. User：用户输入和任务要求。
  3. Assistant：模型的回答，以及工具调用请求。
  4. Tool：工具执行结果，作为后续推理的输入。

Chat Completions 以消息列表为核心。Responses 用更丰富的 Item，可以表达文本、工具调用、工具结果、推理数据和多模态内容。两边都能做多轮对话和工具调用。Responses 的优势是协议更统一，能表达的内容也更多。

上下文放在哪，两边不一样。

Chat 的输入输出就是上面这种 Message。每次请求都带上前面几轮，上下文在本地管理。

Responses 可以把整个会话用请求 ID 连起来。之后每次只带必要字段，服务端按 ID 关联前面几轮。它也支持和 Chat 一样，不把上下文放在服务端，由本地自己管理。我现在用的就是 Responses，并且关掉了服务端存储。

Agent 就是围绕一个目标，持续组织上下文，多轮调用模型，根据模型输出决定下一步，直到任务完成。

任务是否结束，不由单次接口状态决定。两类接口都有响应状态，说明的是这一次调用。

Chat 返回 finish_reason，其中：

  • tool_calls：模型还要调用工具
  • stop：这次生成结束

Responses 返回 status：

status 含义
completed 本次 Response 生成完成
in_progress 正在生成
incomplete 响应未完整完成
failed 执行失败
cancelled 已取消
queued 等待处理

实际决定任务是否结束的是 agent runtime。正常结束，就是没有后续工具调用。异常结束有很多情况，要分开看，不能把一次接口状态当成任务结果。
