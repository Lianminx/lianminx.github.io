  • 服务故障的分层排查网络、进程、数据库与缓存、机器资源、外部依赖、发布，这六层的报错会写成同一种超时。提问也按角色、任务、格式和边界写，避免模型先给一个完整但偏题的方案。
  • 弱网下的大文件分块上传仓库先去掉不参与扫描的目录，压成流，按 4MB 切开，4 路并发。失败按 1、2、4 秒退避，最多 3 次。中断后用 Redis 里已收到的块号续传，合并后再对一次整文件哈希。扫描成功率提高约 40%。
  • 一次联合索引调整的复盘异常统计从 10 秒降到 3 秒后再次变成 16 秒。时间列看起来区分度更高，等它扫出约 600 万行，优化器就放弃了索引。改成先按状态过滤，响应到 1.2 秒。
  • 将高频查询迁移到 Redis策略匹配一次请求打 5 次 MySQL，QPS 约 20，32 核上数据库 CPU 到 3000%。旁路缓存会在冷启动时把数据库打满。改为启动预热、变更双写、10 分钟校对，QPS 到约 600。
  • 短链接服务的缓存一致性与穿透防护读请求拿到旧值、写请求已经删掉缓存、读请求再把旧值写回去。过期时间把这扇窗口收成最终一致。布隆过滤器只负责把「一定不存在」挡在数据库外面。
  • 单机部署的依赖与顺序先确认能登录，再装 JDK 和 Nginx，然后用 Docker 跑 MySQL 和 Redis，最后才拉起业务进程。顺序错了，后面的报错会看起来像应用自己的问题。
  • TCP 三次握手与历史连接第三次确认的是「这个序号是现在这次连接的」。迟到的旧 SYN 如果被当成新连接，双方对连接数量的判断就会不一致。SYN 没有回应时，Linux 默认大约等 63 秒才放弃。
  • Go 内存分配、切片与循环变量new 返回清零后的指针，make 返回已经初始化的切片、map 或 channel。切片没扩容时函数内外指向同一块数组，扩容后就不是。range 的循环变量整个循环只有一份。
  • 消息队列的用途与选型解耦、削峰、分发是三种不同的问题。选型看吞吐、主题规模，以及团队是否已经在运维它。Kafka 快，是因为批量发送、顺序写和分区并行，不是因为某个单点更高效。
  • Agent 的规划、记忆与工具调用规划负责拆任务，短期记忆在上下文里，长期记忆在外部存储。工具调用是思考、行动、观察的循环。事实是否编造，取决于交给模型的目标和工具说明，而不是事后再问一次。
  • Java 集合的默认值与定长列表前缀和计数用 getOrDefault，缺键就是 0。Arrays.asList 返回的列表长度固定，需要增删时再放进新的 ArrayList。
  • 我的 Cursor 协作习惯新项目从空目录开始，先写 README，用 git 保留退路，把反复出现的要求写进 Rules。让模型给每段代码加注释这件事，后来停掉了。
  • Vue 3 中的 ref 与 reactivereactive 不接收简单类型，ref 通过 value 读写，内部仍是 reactive。监听深层字段时返回那个字段，而不是打开 deep。父子组件只通过 props 和 emits 交数据。
  • RPC 调用的接口、传输与服务发现接口侧是动态代理、序列化和异步结果；传输侧是 Netty 的连接、管道和字节缓冲；发现侧是 ZooKeeper 里的节点。先把这三层拆开，再谈框架。
  • 短链接的编码与并发控制原始链接经 MurmurHash 再转成 62 进制。变更走先更新数据库、再删除缓存。修改分组和写入访问统计用读写锁隔开，避免统计打到旧分组上。
